# Mechanical CAD feature coverage

## Approved target

TCAD must provide the **mainstream mechanical CAD capabilities shared by SolidWorks, NX, Onshape, and Creo**. The user's latest 2026-10-10 clarification replaces the earlier full SolidWorks parity target. Equivalent practical workflows remain requirements; vendor-specific niche features are not required solely because one suite offers them. SolidWorks Design 2026 remains one dated reference for the existing inventory; the shared baseline is compared against official documentation from all four applications. TCAD's replaceability, local-file/Git, user-defined presentation, and trackpad requirements remain in scope.

The baseline includes sketching, solids, surfaces, reference geometry, assemblies, manufacturing drawings and tolerancing, sheet metal, weldments, molds, configurations, libraries, inspection, and CAD exchange. Simulation, specialist routing, CAM, electrical design, and PDM product-family parity are outside the clarified baseline. Basic assembly positioning, mechanical mates, collision checks, engineering properties, and local component/version management remain in scope. The [official product matrix](https://www.solidworks.com/sites/default/filesd10/25docs11/SOLIDWORKS_Design_Product_Matrix_October_2025.pdf) provides product context.

This is a requirements inventory and a **code-inspection snapshot**, not a completion claim or a milestone plan. It identifies major families and known modes; toolbar references are not an exhaustive command inventory. Existing rows retain prior gap detail while common practical requirements are checked across the four reference applications. Detailed audits must distinguish shared workflows from vendor-specific optional depth without dropping shared capabilities. Do not calculate a completion percentage from these grouped rows.

## What counts as coverage

For each capability, record its application-owned operation/command identity, schema and adapter versions, supported inputs and modes, geometry limits, and relevant source locations. A complete entry needs:

1. Real evaluated geometry or the appropriate associative CAD data, with f64 authority, explicit units/tolerances, stable identities, and dependencies. Meshes may serve explicitly identified mesh operations and visualization; they do not stand in for required exact B-rep operations.
2. All required modes and practical selection paths, including body/component scope, direction, end conditions, continuity, and configuration behavior where applicable. A limited convex-body shell or ruled loft remains partial.
3. Familiar grouped commands, applicable geometry context actions, task-specific fields, handles and dimensions, and discoverable diagnostics. Publish semantic information/actions independently of user layout and styling. New part geometry starts from sketches.
4. Live asynchronous draft evaluation, current-result validation before OK/Apply, rejection of stale results, Cancel restoring the starting checkpoint, and one undoable commit. Editing downstream dependencies and shared instances must use that same command path.
5. Editable saved definitions, reference reconstruction on rebuild, recoverable failures, and correct manufacturing/export behavior. Unsupported or ambiguous cases must fail clearly and preserve the valid document.
6. Evidence separated by type: implementation inspection, compilation/linting, runtime diagnostics supplied by the user, and user acceptance. Compilation is not evidence that a feature is geometrically complete or usable.

Do not count duplicate labels, dormant schema variants, primitive compatibility operations, placeholder commands, or published dependency capabilities as delivered features. Missing kernel/solver behavior is work within the product scope. Improve or replace implementations behind the contracts as needed.

**Current status labels:** `Partial` means an implementation exists with material limits; `Missing` means this audit found no usable implementation; `Audit` means a broader family needs a detailed mode/format/standard comparison. These labels do not imply interactive acceptance. This update did not run code tests, probes, or manual smoke tests; interactive acceptance belongs to the user.

### Visual presentation update (2026-10-11)

Independent appearance contract v1 supplies clear-anodized-aluminum defaults, named visual presets, part/configuration finish assignments, nested occurrence overrides, pinned PNG/JPEG/TIFF/WebP files, part-local triplanar/planar physical mapping, grayscale height relief, RGB normal and grayscale roughness/metallic/occlusion maps. The viewport adds HDR studio image-based lighting, key/fill controls, exposure, tone mapping and ambient occlusion. Finish and lighting fields/actions use semantic bindings and the shared validated transaction. Engineering materials continue to govern density/mass/BOM independently. True geometric displacement, per-face UV/decals, custom HDR environments, anisotropic highlights and final ray tracing remain gaps; rendered appearance has not received interactive acceptance.
