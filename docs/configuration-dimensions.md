# Configured feature dimensions

Configuration contract version 8 retains the `feature_dimensions` overrides introduced in version 3, stable driving sketch-dimension overrides, and adds scalar expressions for configured native repetition counts. Versions 1–7 definitions and design tables remain readable; new maps are omitted when empty. A feature override stores the feature's stable ID within its owning part, an operation-relative field path, and the replacement expression or count source. Base definitions remain unchanged. Renaming or reordering a feature does not retarget its dimensional overrides.

The docked Configurations editor now has a Feature dimensions section grouped by feature. Its checkbox makes the value explicit in the current configuration; clearing it restores the inherited value. The Design table contains the same dimension cells alongside named parameter columns. The feature/field filter and horizontal scrolling keep larger tables usable. Derived configurations inherit individual dimensional fields, so a child can override an extrusion depth while inheriting its parent's draft angle or thin wall thickness. Duplicate copies the resolved dimensional expressions along with the other resolved overrides.

Fields are discovered from actual application-owned `Expr` members in the current operation definition. This includes ordinary extrude distances and offsets, revolve angles, radii, chamfer distances, shell thicknesses, dimensional feature options, datum expressions, solid/surface controls, and manufacturing expressions where those operation fields are present. Field adapter version 4 also discovers actual unsigned repetition fields named count, counts, copies, instances, sides, rows, or columns. These accept exact unsigned integer literals or scalar expressions such as `@copies * 2` and `@Assembly1::rows + 1`, retaining their native integer bounds and operation validation. Names, topology references, source IDs, mode strings, literal text, numeric placements, and adapter versions are not reclassified. Optional modes must be enabled in the feature's definition before their fields can be configured. Ordinary operation JSON retains its native integer fields and is unchanged by discovery.

Count expressions are resolved after every active part and assembly parameter scope has received its inherited configuration overrides. A target's named variant uses its own base parameters plus its inherited overrides, alongside the selected sibling parameter scopes. Expressions must produce finite, nonnegative integral scalars; length/angle units, fractional values, missing or ambiguous parameters, dependency cycles and overflow fail explicitly. No rounding or clamping occurs. Expressions follow TCAD's f64 expression authority and may produce at most `2^53−1`; exact unsigned literals bypass f64 and retain the full native integer range. The resolved integer must also fit its operation field. Operation-specific constraints remain in force: for example, body patterns allow 1–10000 total positions, including both directions and the seed, and validate skipped positions against the configured counts.

The native table displays the resolved count next to its equation. Portable controls publish the authored equation, resolved count or error, native maximum and expression maximum. These values are evaluated from the current configuration source, including edited parameters and inheritance. Changing a parameter or count immediately submits the configured draft to the normal worker; OK still requires its current valid result. Count validation uses parameter-only contexts and never calls geometry materialization recursively. Local component variants retain their parent parameter context; the external equation proof includes authored count sources even after they become native integers, so unsupported occurrence-driven geometry fails instead of sharing a wrongly configured mesh.

Object field names retain RFC 6901 escaping (`~0` for `~`, `~1` for `/`). Arrays of authored records use `@id=RECORD_ID` segments rather than their current numeric positions. For example, `/definition/placements/@id=placement-record-7/angle` selects that saved placement record even when the table is reordered. Resolution requires one matching record; deletion, a missing ID, or a duplicate ID produces an explicit error. The current resolved numeric JSON pointer is metadata, never the stored identity. Numeric overrides into records with authored IDs are rejected, including old positional paths from version 2: replace them with the corresponding identified field instead of allowing a silent rebind.

Arrays without authored record IDs retain numeric positions. This includes fixed vectors and anonymous option records such as per-face wall-thickness records or legacy bend rows. Reordering, inserting or deleting anonymous records can change which slot a positional override addresses; no stable-record association is claimed for these sources. Semantic fields expose `positional: true` when any such slot occurs along the path. Native table headers retain the current readable numeric position while the exported column and Advanced Source retain the stable field identity where one exists.

CSV dimension columns use `dimension:FEATURE_ID:/field/path`. For example:

```csv
name,dimension:Boss-Extrude1:/distance,dimension:Boss-Extrude1:/options/start_offset
Short,25 mm,
Long,@stock_length,2 mm
```

On import, a feature may be specified by its stable ID or its unique name in that table's owning part. Paths must match real typed expression or repetition-count fields in that feature's current operation. Unknown or ambiguous names, foreign-owner features, unsupported fields, removed option fields, and malformed values produce explicit errors. CSV export uses stable feature IDs; empty cells inherit. JSON import/export preserves the complete nested override map and version. Import validates a candidate document before replacing the caller's definitions, so a failed import leaves them unchanged. Existing merge/replace, parent, active selection, unit expression, and atomic local write behavior applies to these columns too.

Inherited field expressions are installed before the worker evaluates configured geometry. They therefore use the same unit rules, parameter dependency resolution, geometry validation, and configured part/subassembly identities as ordinary feature expressions. Simultaneous component variants use independent effective operation definitions. Invalid units or impossible geometry remain visible as draft evaluation errors and block confirmation. Edits use the common editor checkpoint and persistent worker; current validation is required for OK, and Cancel restores the starting document and selection. No geometry surrogate or unvalidated commit is introduced.

Portable semantic bindings expose `feature-dimension-source` metadata and `configuration-dimension-field` expression and override controls. Editable controls publish the `configuration-dimension` value adapter with owner, configuration, feature, field path, field kind, current pointer, and positional status. Readers resolve current draft values and setters revalidate identities and the editor checkpoint before routing through the shared document draft. Controls can be placed or repeated in user layouts, and their stable IDs can be styled independently of the native table. Library insertion and Make Unique remap dimensional feature ownership and authored record selectors while preserving expression text and literal operation field names.

Sketch overrides use `sketch_dimensions[SKETCH_ID][CONSTRAINT_ID]` and CSV columns `sketch-dimension:SKETCH_ID:CONSTRAINT_ID`. The sketch owner may use its unique name on import; constraint references remain stable IDs. The docked editor and filtered design table expose saved driving coordinates, lengths, gaps, angles and size dimensions. Child configurations inherit each dimension independently. Values are installed before native sketch solving, so normal expression units, parameter references and validation govern the result. The saved ordinate/baseline/chain group entries use these same driving constraint IDs and are configurable through the same columns; semantic descriptors retain the group ID. Missing, duplicate, deleted, geometric-only or reference/driven constraints are rejected. Changing a driving dimension to a reference measurement requires removing its configuration overrides first. Portable `sketch-dimension-source` and `configuration-sketch-dimension-field` controls publish the same stable identities and version 1 contract; library insertion remaps both sketch and constraint IDs.

Other literal numeric fields, spreadsheet-linked workbooks and flexible assembly variants remain gaps. Counts configured here do not turn every unconfigured base operation into an equation editor; the existing native integer source remains intact. Compilation, formatting, and linting validate this implementation; interactive acceptance remains with the user, and no tests or manual smoke tests were added or run.
