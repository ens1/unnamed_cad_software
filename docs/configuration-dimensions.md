# Configured feature dimensions

Configuration contract version 3 stores `feature_dimensions` in native overrides. Version 1 and 2 definitions and design tables remain readable; the new map is omitted when empty. A configuration stores the feature's stable ID within its owning part, an operation-relative field path, and the replacement expression text. Base feature definitions remain unchanged. Renaming or reordering a feature does not retarget its dimensional overrides.

The docked Configurations editor now has a Feature dimensions section grouped by feature. Its checkbox makes the value explicit in the current configuration; clearing it restores the inherited value. The Design table contains the same dimension cells alongside named parameter columns. The feature/field filter and horizontal scrolling keep larger tables usable. Derived configurations inherit individual dimensional fields, so a child can override an extrusion depth while inheriting its parent's draft angle or thin wall thickness. Duplicate copies the resolved dimensional expressions along with the other resolved overrides.

Fields are discovered from actual application-owned `Expr` members in the current operation definition. This includes ordinary extrude distances and offsets, revolve angles, radii, chamfer distances, shell thicknesses, dimensional feature options, datum expressions, solid/surface controls, and manufacturing expressions where those operation fields are present. Names, topology references, source IDs, mode strings, literal text, numeric placements, legacy integer counts, and sketch solver constraints are not reclassified as feature expression fields. Optional modes must be enabled in the feature's definition before their fields can be configured. The field adapter is version 2 and uses the existing Serde `Expr` type marker; ordinary document JSON is unchanged by discovery.

Object field names retain RFC 6901 escaping (`~0` for `~`, `~1` for `/`). Arrays of authored records use `@id=RECORD_ID` segments rather than their current numeric positions. For example, `/definition/placements/@id=placement-record-7/angle` selects that saved placement record even when the table is reordered. Resolution requires one matching record; deletion, a missing ID, or a duplicate ID produces an explicit error. The current resolved numeric JSON pointer is metadata, never the stored identity. Numeric overrides into records with authored IDs are rejected, including old positional paths from version 2: replace them with the corresponding identified field instead of allowing a silent rebind.

Arrays without authored record IDs retain numeric positions. This includes fixed vectors and anonymous option records such as per-face wall-thickness records or legacy bend rows. Reordering, inserting or deleting anonymous records can change which slot a positional override addresses; no stable-record association is claimed for these sources. Semantic fields expose `positional: true` when any such slot occurs along the path. Native table headers retain the current readable numeric position while the exported column and Advanced Source retain the stable field identity where one exists.

CSV dimension columns use `dimension:FEATURE_ID:/field/path`. For example:

```csv
name,dimension:Boss-Extrude1:/distance,dimension:Boss-Extrude1:/options/start_offset
Short,25 mm,
Long,@stock_length,2 mm
```

On import, a feature may be specified by its stable ID or its unique name in that table's owning part. Paths must match real typed expression fields in that feature's current operation. Unknown or ambiguous names, foreign-owner features, non-expression fields, removed option fields, and malformed expression tokens produce explicit errors. CSV export uses stable feature IDs; empty cells inherit. JSON import/export preserves the complete nested override map and version. Import validates a candidate document before replacing the caller's definitions, so a failed import leaves them unchanged. Existing merge/replace, parent, active selection, unit expression, and atomic local write behavior applies to these columns too.

Inherited field expressions are installed before the worker evaluates configured geometry. They therefore use the same unit rules, parameter dependency resolution, geometry validation, and configured part/subassembly identities as ordinary feature expressions. Simultaneous component variants use independent effective operation definitions. Invalid units or impossible geometry remain visible as draft evaluation errors and block confirmation. Edits use the common editor checkpoint and persistent worker; current validation is required for OK, and Cancel restores the starting document and selection. No geometry surrogate or unvalidated commit is introduced.

Portable semantic bindings expose `feature-dimension-source` metadata and `configuration-dimension-field` expression and override controls. Editable controls publish the `configuration-dimension` value adapter with owner, configuration, feature, field path, field kind, current pointer, and positional status. Readers resolve current draft values and setters revalidate identities and the editor checkpoint before routing through the shared document draft. Controls can be placed or repeated in user layouts, and their stable IDs can be styled independently of the native table. Library insertion and Make Unique remap dimensional feature ownership and authored record selectors while preserving expression text and literal operation field names.

Configuration-specific sketch solver dimensions, configuration columns for non-expression numeric/integer fields, spreadsheet-linked workbooks, display states, and flexible assembly variants remain separate work. Compilation, formatting, and linting validate this implementation; interactive acceptance remains with the user, and no tests or manual smoke tests were added or run.
